# 지침 문서 점검

## 이 절차가 막으려는 것

문서 점검을 문장 다듬기로 대신하면 문서는 매끈해지면서 틀린 채로 남는다.

- `AUTHORING.md`의 Java 강조 설명이 현재 동작과 반대였다. 강조 범위를 넓힌 커밋이 문서를 건드리지 않았고, 문장만 읽어서는 어긋난 것을 알 수 없었다.
- 비교 콜아웃의 근거 수치(`703px`, `324px`)가 낡아 있었다. 콜아웃 테두리를 바꾼 커밋이 이 숫자의 전제를 무너뜨렸는데, 숫자를 적은 문서는 그대로였다.

둘 다 코드를 열어야 찾을 수 있었다. 그래서 이 절차는 사실 대조를 먼저 하고 문장은 마지막에 손댄다.

사실 대조만 하면 반대로 문서가 정확해지면서 계속 길어진다. 빠진 것을 보충하는 만큼 문장이 쌓이고, 구현의 세부를 옮겨 둔 문장은 구현이 바뀔 때마다 다시 틀린다. 그래서 4단계에서 문장마다 그 문서에 있어야 하는지를 따로 묻는다.

## 1. 기준 확인

대상 문서의 정본 기준을 먼저 편다. 기준은 문서마다 다르다.

| 문서 | 기준 |
|---|---|
| `DESIGN.md` | google-labs-code/design.md의 명세와 PHILOSOPHY, `npm run design:lint` |
| `AGENTS.md`, `CLAUDE.md`, `src/lib/AGENTS.md` | agents.md 사이트의 권장 절, Claude Code 메모리 문서(분량·구조·구체성), Codex의 AGENTS.md 탐색 방식 |
| `AUTHORING.md` | 구현 코드와 vault의 `99_Templates/_property-schema.md` |

저장소 공통 기준인 문체와 종결체는 `AGENTS.md`의 「한국어 문체」 절이 정본이다. 이 스킬에는 규칙을 옮겨 적지 않는다. 옮겨 적으면 규칙이 바뀔 때 두 곳이 어긋난다.

## 2. 측정

```bash
python3 .agents/skills/doc-audit/scripts/measure.py AGENTS.md
```

절별 크기, 400자가 넘는 문단, 헤딩 구조, em/en dash를 한 번에 본다. 줄 수보다 바이트를 본다. `AGENTS.md`와 `CLAUDE.md`는 매 세션 통째로 실리므로 크기가 곧 비용이고, 188줄짜리 문서가 23KB인 일이 실제로 있었다. 한 절이 전체의 4분의 1을 넘거나 한 문단이 1,000자를 넘으면 그 자리를 구조 후보로 적어 둔다.

## 3. 사실 대조

이 단계가 점검의 본체다. 문서에서 검증할 수 있는 서술을 항목으로 뽑는다. 수치, 파일·함수 이름, 목록(언어·피드·사용처), 조건문("~면 빌드가 실패한다"), "어느 테스트가 무엇을 검사한다"는 서술이 대상이다. 테스트 서술은 파일이 있는지가 아니라 그 단언이 실제로 있는지까지 본다. `DESIGN.md` 대응 표에서 파일은 있는데 해당 단언이 없는 줄이 네 개 나왔다.

항목이 열 개를 넘으면 읽기 전용 에이전트에 나눠 맡긴다. 파일 범위가 겹치지 않게 두세 갈래로 자르고, 각 갈래에 이런 형식으로 지시한다. 행 번호는 파일을 직접 읽은 값으로 적는다. 세션 맥락에 실린 사본에서 옮기면 번호가 어긋난다.

```
`AUTHORING.md`의 <주제> 서술이 현재 구현과 일치하는지 확인한다. 소스와 문서는 읽기만 하고 고치지 않는다.
주로 볼 파일은 <파일 목록>이다.
항목마다 판정을 `일치`, `다름`, `문서에 없음` 중 하나로 적고, 근거 파일과 줄 번호를 함께 적는다.
`다름`이면 현재 구현의 실제 동작을 한 문장으로 적는다.
1. (12행) <문서의 서술을 그대로 옮긴 문장>
2. ...
```

하위 에이전트의 보고는 근거이지 결론이 아니다. 수치와 반대로 읽히는 서술은 직접 파일을 열어 확인한 뒤 보고에 쓴다.

### 구현에서 문서로 되짚기

문서에 적힌 것만 대조하면 **처음부터 빠진 내용은 검사 대상에 들어오지 않는다.** 문서를 마지막으로 고친 뒤의 구현 변경에서 출발해 반대 방향으로 한 번 더 본다.

```bash
git log -1 --format=%h -- AUTHORING.md          # 문서를 마지막으로 고친 커밋
git log --oneline <그 커밋>..HEAD -- src         # 그 뒤의 구현 변경
```

각 변경에 대해 이렇게 묻는다. 셋 중 하나라도 그렇다면 문서에 한 줄이 필요하다.

- 작성자가 노트나 코드를 다르게 쓰게 되는가.
- 독자가 보는 결과가 달라지는가.
- 지키지 않으면 빌드나 검사가 실패하는가.

모든 구현 세부를 문서로 옮기지는 않는다. 위 세 질문에 모두 아니라면 코드를 읽으면 알 수 있는 사실이므로 문서에 넣지 않는다. 어두운 화면의 코드 강조색과 썸네일 밝기가 `AUTHORING.md`에 통째로 빠져 있었던 것은 이 되짚기로 찾은 종류의 누락이다.

## 4. 필요성, 중복, 문체

- **필요성**: 문장마다 그 문서의 독자에게 필요한지 묻는다. 기준은 3단계의 세 질문이고, 방향만 반대다. 셋 다 아니라면 새로 넣지 않을 뿐 아니라 이미 있는 문장도 지운다.
  - 틀린 문장이 세 질문에 걸리지 않으면 고치지 않고 지운다. 고친 문장은 다음 구현 변경에서 또 틀린다.
  - 화면 수치(px)와 규칙 목록의 세부는 작성자나 독자가 겪는 결과 한 문장으로 줄인다. 세부는 코드 주석과 테스트가 관리한다.
  - "~했더니 ~였다" 같은 결정 과정은 커밋에 두고, 문서에는 지금 지키는 규칙과 그 이유만 남긴다.
  - 다른 문서가 관리한다는 이유로 지우면 그 문서에 실제로 있는지 확인한다. 어디에도 남지 않게 되는 내용은 지우기 전에 보고한다.
- **중복**: 다른 지침 문서와 겹치는 문장을 찾는다. 겹치면 한쪽이 관리하고 다른 쪽은 가리킨다. 어느 쪽이 관리할지는 독자로 정한다. 화면의 값은 `DESIGN.md`, 저장소에서 일하는 방법은 `AGENTS.md`, 노트가 사이트에 나오는 방식은 `AUTHORING.md`다.
- **문체**: 「한국어 문체」 절로 본다. 자주 걸리는 것은 비유 어휘("돈다", "물린다", "통로"), 서술어 없이 끝나는 문장, "~할 때"로 끝나는 부사절 헤딩, 같은 문장의 반복이다.
- **읽는 자리**: 문서가 실제로 열리는 곳에서 링크가 동작하는지 본다. GitHub에서 읽는 문서에 vault 위키링크를 쓰면 링크가 아니라 글자로 보인다.

## 5. 보고와 범위 합의

고치기 전에 발견을 보고한다. 발견은 고치는 방법이 다른 네 부류로 나눈다.

- 문서만 틀린 것: 문서를 구현에 맞추면 끝난다.
- 문서가 규칙으로 선언했는데 구현이 따르지 않는 것: 문서와 구현 중 어느 쪽을 고칠지 사용자가 정한다. 테스트의 검사 범위에 빈틈이 있는 자리에서 주로 생긴다.
- 빠진 것: 3단계의 세 질문을 통과한 것만 올린다.
- 필요성, 중복, 문체.

점검 중에 찾은 틀린 코드 주석은 문서 범위 밖이므로 따로 적는다.

사용자가 이미 고칠 범위를 말했으면 그 요청을 따르고, 범위가 불분명하거나 발견이 요청보다 넓을 때만 확인한다. 물을 때는 그 도구에서 쓸 수 있는 수단을 쓴다(Claude Code는 `AskUserQuestion`, Codex는 본문 질문). 선택지는 위 부류대로 독립적으로 고를 수 있게 나눈다. 큰 재정리를 제안할 때는 절 이름을 가리키는 앵커 링크가 깨지는지 먼저 확인한다.

```bash
git grep -n "AUTHORING.md#"
```

## 6. 반영과 검증

```bash
python3 .agents/skills/doc-audit/scripts/carryover.py AUTHORING.md
python3 .agents/skills/doc-audit/scripts/measure.py AUTHORING.md --names
```

- `carryover.py`는 커밋된 판의 문장을 그대로·바뀜·사라짐으로 가른다. 절을 크게 옮길 때 문장이 조용히 사라지는 것을 막는다. `사라짐`은 하나씩 의도한 삭제인지 확인하고, `바뀜`은 짝을 읽어 뜻이 뒤집히거나 조건이 빠지지 않았는지 본다. 실제로 이 검사에서 되살린 문장이 있었다.
- `--names`는 문서가 백틱으로 가리키는 파일 경로가 실제로 있는지 본다.
- 문서만 고쳤더라도 `npm test`와 `npm run build`를 돌린다(`AGENTS.md` 「명령」). 문서 값을 검사하는 테스트가 있다.
- 커밋과 반영 방법(main push, 브랜치, 보류)은 이미 받은 요청이 있으면 그대로 따르고, 없으면 묻는다(`AGENTS.md` 「커밋 규칙」).

## 흔한 함정

- 문장을 다듬는 것으로 점검을 대신하지 않는다. 다듬기는 사실 대조가 끝난 뒤에 한다.
- 원인을 추측해서 보고하지 않는다. 코드를 읽고 재현한 뒤 쓴다.
- 구현의 예외를 문서에 옮길 때 이유를 지어내지 않는다. 코드 주석과 커밋에서 이유를 찾지 못하면 사실만 적고 사용자에게 묻는다. 그럴듯한 이유를 적으면 다음 점검에서 검증할 근거가 없다.
- 보충하라는 요청을 문서를 늘리라는 뜻으로만 받지 않는다. 보충과 함께 줄일 자리를 찾는다.
- 기준과 규칙을 이 스킬에 복사하지 않는다. 정본을 가리킨다.
- 분량을 줄이라는 요구를 문장에서 조사와 어미를 덜어내는 것으로 오해하지 않는다. 줄이는 것은 문장 수다.
