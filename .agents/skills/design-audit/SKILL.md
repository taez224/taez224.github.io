# 실제 화면 디자인 점검

## 기준과 범위

저장소 루트를 기준으로 `DESIGN.md`의 Overview, 대상 화면에 해당하는 절, 「문서와 구현의 대응」과 「검사」를 읽는다. 색·글꼴·간격·아이콘·움직임의 규칙과 검사할 화면 조건은 그 문서에서 가져온다. 이 스킬에는 값을 복제하지 않는다. 실행 명령과 작업 규칙은 `AGENTS.md`를 따른다.

사용자가 지정한 화면과 행동부터 살핀다. 전체 점검이면 Overview의 독자가 실제로 수행할 경로를 골라 확인한다. 예를 들어 저자가 궁금한 방문자는 홈에서 대표 글을 읽고 소개로 이동하며, 검색으로 들어온 독자는 본문을 읽고 관련 노트를 따라간다. 이 경로에서 독자가 막히는 지점과 저자의 판단을 확인할 수 있는지를 본다.

점검 요청은 진단과 제안까지로 다룬다. 이미 수정할 범위를 승인받았다면 그 범위의 구현과 검증까지 진행하며, 진단을 이유로 승인을 반복해서 요구하지 않는다. 요청 밖에서 발견한 문제는 별도로 보고한다.

## 화면 관찰

먼저 현재 화면을 브라우저에서 열고 대상 URL, 실행 중인 빌드, 화면 크기, 테마, 글자 설정, 입력 방식과 재현 순서를 기록한다. 로컬 화면과 배포 화면이 같은 구현이라고 가정하지 않는다. 첨부 이미지로만 확인한 사항과 직접 조작해 확인한 사항을 구분한다. 브라우저를 사용할 수 없으면 화면 검증을 완료했다고 보고하지 않는다.

관련된 항목을 골라 실제 콘텐츠와 조작으로 확인한다.

- **읽는 순서:** 처음 보이는 제목·요약·보조 정보 중 무엇이 먼저 눈에 들어오는지, 제목만 훑어도 글을 고를 수 있는지 확인한다. 긴 제목과 한국어·영문이 섞인 문단에서 줄바꿈과 정렬을 본다.
- **탐색과 복귀:** 링크가 예상한 곳으로 가는지, 도착한 화면에서 맥락을 이해할 수 있는지 확인한다. 검색·목차·지도 패널을 열고 선택한 뒤 닫기와 뒤로 가기로 돌아오는 흐름을 끝까지 수행한다.
- **반응형 배치:** 넓은 화면과 좁은 화면 사이에서 폭을 연속으로 바꾼다. 열이 바뀌는 순간의 겹침·잘림·불필요한 빈자리와 보조 정보의 순서를 본다. 검사 폭과 상태는 DESIGN.md에서 읽는다.
- **조작과 상태:** 마우스 호버에만 의존하는 정보, 터치 영역과 눈에 보이는 기호의 차이, 키보드 포커스와 순서를 확인한다. 관련 기능의 성공·실패·빈 상태도 실제로 연다.
- **시각적 균형:** 아이콘과 글자의 기준선, 반복 행의 정렬, 밝은 화면과 어두운 화면의 식별성을 비교한다. 광학 보정이 필요해 보이면 SVG 도안과 CSS 상자를 구분해 확인한다. 화면을 확대해 본 인상만으로 위치를 옮기지 않고 실제 배율에서도 비교한다.
- **저자의 개성:** 소개와 대표 글이 이 저자의 경험·관심·판단을 구체적으로 보여 주는지 본다. 장식이 독자의 이해를 돕는지, 글의 차이를 가리는지 확인한다. 문구와 원고는 소개 원고 작업과 글쓰기 규칙이 다루므로, 발견한 점을 보고하고 고치지 않는다.

아이콘 세트, 카드 배치, 특정 단어만으로 AI가 만들었다고 판정하거나 일괄 교체하지 않는다. 어울리지 않는다고 판단하면 현재 콘텐츠에서 생기는 문제와 기존 디자인 의도를 근거로 설명한다. 사용자 취향에 따른 대안은 동작 결함과 구분하며, 문제가 없는 요소까지 변경 후보로 채우지 않는다.

## 발견과 제안

발견마다 다음 정보를 짧게 남긴다. 관련 화면 캡처나 재현 링크를 붙이고, 원인 코드는 확인한 경우에만 연결한다.

- 어떤 화면 조건과 행동에서 무엇을 관찰했는지 적는다.
- 독자가 읽거나 행동하는 데 어떤 영향을 주는지 설명한다. 관찰한 사실과 추정하는 영향을 구분한다.
- 기존 규칙과의 불일치인지, 사용성 문제인지, 비교해 볼 취향 제안인지 밝힌다.
- 가장 작은 수정안과 그 결과를 확인할 방법을 적는다. 얻는 것과 잃는 것이 있으면 함께 설명한다.

우선순위는 행동을 막는 문제, 읽거나 탐색할 때 반복해서 생기는 불편, 미세한 시각 조정 순으로 판단한다. 보기 좋다는 이유만으로 기능 추가를 앞세우지 않는다. 전면 재설계보다 현재 구조에서 문제를 해결할 수 있는지 먼저 검토한다.

## 변경 전후 검증

변경 전 화면과 재현 조건을 남긴 뒤 원인에 해당하는 부분을 고친다. 취향이 갈리는 변경은 후보 여러 개를 실제 색과 글꼴로 만들어 같은 콘텐츠·폭·테마·스크롤 위치에서 나란히 보여 주고, 사용자가 고르게 한다. 흔한 기본 모양은 후보로 내지 않고, 서로 다른 변경을 한 후보에 섞지 않는다. 비교에는 문제가 실제로 드러나는 콘텐츠와 입력을 고른다. 짧은 분류만 나오는 검색어로는 분류가 두 줄로 갈라지는 문제가 보이지 않았다. 보고서나 비교 파일은 `docs/`에 저장한다(`AGENTS.md` 「작업 규칙」).

수정 뒤에는 발견한 문제가 사라졌는지 같은 행동으로 확인한다. 이어서 DESIGN.md의 검사 조건으로 인접 화면과 상태도 확인한다. 기능을 열어 보는 데서 끝내지 않고 선택·닫기·복귀까지 수행한다. 실제 vault는 화면 관찰용으로만 읽고 회귀 테스트의 입력은 저장소 테스트 규칙을 따른다.

자동 검사 결과와 실제 화면 확인 결과를 나눠 보고한다. 캡처는 배치를 보여 주지만 입력 동작을 증명하지 않으며, 테스트 통과도 광학적 균형이나 문구의 적절함을 보장하지 않는다. 확인하지 못한 브라우저나 상태는 남은 검증으로 명시한다.

보고에는 중요한 발견, 반영한 변경, 확인한 화면 조건, 남은 불확실성을 남긴다. 새 디자인 규칙이 필요해졌다면 화면 검증 근거를 먼저 제시하고, 정본 문서의 변경은 doc-audit 절차로 다룬다.
